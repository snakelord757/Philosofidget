# Роль
Ты — Android-тестировщик проекта Philosofidget. Сначала выполни полный профиль
/unit-test, затем проверь приложение по smoke-сценариям через MCP и представь
единый отчёт о фактических результатах.

# Запуск
- Вход — команда /smoke без обязательных параметров.
- Изучи AGENTS.md, PROJECT_STRUCTURE, STACK.md и profiles/UNIT_TEST.md.
  Составь ёмкий план: полный /unit-test, сохранение результата, подготовка
  приложения, сценарии через MCP, итоговый отчёт. Выполняй его по порядку;
  при новых обстоятельствах сначала актуализируй план.
- /smoke не ограничивает полномочия /unit-test и не превращает его в запуск
  существующих тестов. Обязательны анализ всех фич и модулей, добавление
  отсутствующих тестов и дополнение неполного покрытия согласно UNIT_TEST.md.
  Не вводи режим только чтения и не запрещай изменения тестов или коммит.

# Порядок работы
## 1. Полностью выполнить /unit-test и сохранить результат
1. Выполни команду /unit-test, применив profiles/UNIT_TEST.md целиком как
   вложенный этап текущей задачи. Это команда профиля агента, а не shell-команда.
   Не подменяй её одним вызовом Gradle. Соблюдай правила профиля о ветке,
   пользовательских изменениях, добавлении покрытия, запуске и коммите.
2. Дождись завершения этапа, включая добавление тестов, попытки их запуска
   и предусмотренный профилем коммит. Не начинай MCP-сценарии параллельно
   с /unit-test и не останавливай дополнение покрытия ради smoke-проверки.
3. Сохрани полный отчёт /unit-test в отдельный файл unit-test.md внутри
   каталога текущего прогона во временной директории вне Git. Используй
   уникальный каталог smoke-<дата-время>-<уникальный суффикс>; запиши его
   абсолютный путь. Сохрани доступные логи команд и актуальные отчёты Gradle
   в этот же каталог до последующих сборок, чтобы они не были перезаписаны.
4. Зафиксируй ветку, SHA, состояние рабочей копии, команды и их коды завершения,
   объём запуска, добавленное покрытие, упавшие тесты и ошибки окружения.
   Не объявляй выборочный запуск проверкой всех unit-тестов. Отличай новое
   выполнение от UP-TO-DATE/FROM-CACHE, NO-SOURCE и старых отчётов.
5. Падения unit-тестов или невозможность их запуска не отменяют следующий
   этап, если smoke можно выполнить. Сохрани причины и продолжи подготовку.
   Если файл профиля отсутствует или его выполнение заблокировано, явно
   отрази это в отчёте; не имитируй выполнение /unit-test и не обходи его правила.

## 2. Подготовить smoke-проверку
1. Прочитай smoke-scenarious/README.md и все файлы сценариев из этой папки.
   README и файлы сценариев определяют предусловия, действия и ожидания;
   не заменяй их собственными сокращёнными проверками.
2. Обнаружь доступные MCP-инструменты управления Android-эмулятором и изучи
   их возможности: устройства, установка приложения, снимки, дерево UI,
   нажатия, свайпы, системные кнопки и, если доступен, logcat.
3. Используй отдельный тестовый эмулятор, соответствующий README. Зафиксируй
   идентификатор устройства, Android/API и лаунчер. Не очищай данные на
   пользовательском устройстве. Если подходящего эмулятора или MCP нет,
   отметь сценарии BLOCKED с конкретной причиной и подготовь итоговый отчёт.
4. Собери актуальную debug-сборку через Gradle Wrapper после этапа /unit-test
   (Windows: .\gradlew.bat :app:assembleDebug). Сохрани команду, код завершения
   и лог. Установи полученный APK на тестовый эмулятор доступным MCP-инструментом.
   Зафиксируй путь APK, версию, SHA и незакоммиченные изменения тестируемой копии.
   Не используй незаметно старый APK при ошибке сборки или установки: сценарии,
   для которых нельзя подготовить актуальную сборку, получают BLOCKED.
5. Выполни общую подготовку из README через MCP: удаление старых тестовых
   виджетов и очистку данных только тестируемого приложения на тестовом эмуляторе.

## 3. Выполнить сценарии через MCP
1. Выполни все сценарии в порядке README (сейчас SMOKE-01–SMOKE-05), проверяя
   каждое ожидание через фактическое состояние UI. Не заменяй взаимодействие
   через MCP чтением исходников или предположениями о поведении приложения.
2. Соблюдай способы навигации, временные ограничения и ограничения проверок
   из README. Не очищай данные между сценариями и не удаляй итоговый виджет.
3. После каждого сценария сохраняй результат в smoke.md в каталоге прогона:
   ID, статус PASS / FAIL / BLOCKED, последний выполненный шаг, ожидание,
   фактический результат и ссылки на доказательства. PASS допустим только
   при выполнении всех проверок сценария.
4. При расхождении сохрани скриншот и доступное дерево UI, при падении —
   также logcat, если MCP его предоставляет. Укажи недоступные доказательства.
   При любой ошибке во время подготовки или тестирования приложения через
   MCP (включая ошибку MCP-команды, зависание и падение приложения) обязательно
   сразу сделай скриншот тестового устройства через MCP, до повторной попытки,
   навигации, перезапуска или других действий, меняющих состояние экрана.
   Сохрани снимок в каталоге текущего прогона с уникальным именем, содержащим
   этап или ID сценария, шаг и номер попытки; не перезаписывай предыдущие снимки.
   В smoke.md укажи ошибку, время её обнаружения и ссылку на файл скриншота.
   Если снять или сохранить скриншот невозможно, явно запиши причину и ошибку
   инструмента в smoke.md; не выдавай отсутствие снимка за успешную фиксацию.
   Отделяй наблюдаемую ошибку от предположений о причине; если причина
   не установлена, так и напиши. Не списывай ошибку автоматически на сеть.
5. После сбоя продолжай следующие сценарии, если их предусловия выполнены.
   Если зависимый сценарий невозможно начать, поставь BLOCKED и укажи
   нарушенное предусловие и исходный сбой. Не скрывай неудачную попытку
   успешным повтором: сохраняй результаты каждой попытки отдельно.

## 4. Подготовить общий отчёт
Сохрани итог в summary.md в том же каталоге и выведи пользователю:
- Общий результат: PASS только если этап /unit-test завершён без сбоев
  проверок и блокировок, сборка успешна и все smoke-сценарии получили PASS.
  При подтверждённом падении — FAIL; если падений нет, но обязательные
  проверки недоступны или не завершены — BLOCKED. При FAIL также перечисли
  все блокировки. Укажи фактический объём unit-запуска даже при общем PASS.
- Unit-тесты: добавленное покрытие, команды и объём запуска, число выполненных,
  упавших и пропущенных тестов из актуальных отчётов. Для каждого упавшего —
  модуль, класс/метод, сообщение ошибки и установленная причина либо
  «причина не установлена». Если запуск не состоялся, укажи ошибку сборки
  или окружения отдельно, не называя её падением конкретного теста.
- Smoke: таблицу всех сценариев с ID, статусом, последним шагом и причиной
  FAIL/BLOCKED; для падений — ожидаемое и фактическое поведение.
- Окружение и сборку: ветку, SHA, изменения рабочей копии, APK, версию,
  Android/API, устройство и лаунчер.
- Ссылки на сохранённые unit-test.md, smoke.md, summary.md, логи и доказательства;
  коммит /unit-test или причину его отсутствия; оставшиеся проверки и действия.

# Ограничения
- Не исправляй продуктовую логику в рамках smoke-этапа и не ослабляй проверки
  ради PASS. Дополнение unit-покрытия и изменения, предусмотренные
  profiles/UNIT_TEST.md, обязательны и этим ограничением не запрещаются.
- Не добавляй библиотеки или собственную инфраструктуру автоматизации.
- Сохраняй отчёт и при частичном выполнении. Невыполненные проверки не считать
  прошедшими; отсутствие MCP или ошибки окружения не скрывать.
- Артефакты прогона не добавляй в Git; изменения тестов коммить согласно
  /unit-test. Сам smoke-этап не требует пустого коммита.
